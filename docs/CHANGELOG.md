# Changelog — quorum-mcp

Chronological, append-only record of completed waves and dated fixes for the `quorum-mcp` repo. `CLAUDE.md` stays a concise current-state reference (architecture constraints, non-negotiable rules); this file is the history behind it. See also the `quorum` repo's [docs/CHANGELOG.md](../../quorum/docs/CHANGELOG.md) for gateway-side wave entries.

**Post-Wave-G additions (complete):**
- `src/graph/client.js` `callGraphiti()`: fixed `X-Quorum-Project` header derivation in gateway mode. It previously read `params.group_id` (singular) to build the header, but Wave B's `searchNodes`/`searchFacts` send `params.group_ids` (plural array) — that field was always `undefined`, so the header silently never went out and every `search_nodes`/`search_memory_facts` call 400'd against the gateway proxy's own `"X-Quorum-Project header required"` guard (`gateway/src/routes/graphiti.js:29`). Fixed by reading the project ID from `GatewayClient.getProjectId()` (new getter, `src/gateway/client.js`) instead — the same authoritative value already used for `/pg/*` and `/config/*` calls, kept in sync per-call via `setProjectId()` in `src/server.js`. No vendored-copy sync needed: the gateway's own `gateway/src/shared/graph/client.js` doesn't have this JWT-attach logic (it calls Graphiti directly, never proxies through itself). Regression tests added in `tests/gateway/graph-client.test.js` (gateway mode previously had zero coverage in that file — all existing tests forced direct mode).
- `src/graph/schema.js`: `Standard` entity type added — org-wide baseline measured by conformance scoring; properties: `scope`, `rationale`, `exception_process`, `domain`. `Guideline` entity type added — recommended practice with allowed exceptions; properties: `rationale`, `when_to_deviate`, `domain`. Both synced from canonical `gateway/src/shared/graph/schema.js`. `Standard` is the preferred type for global catalog entries.
- Hierarchy `org` tier: valid levels in `HierarchySchema` now `org → group → division → department → service` (5 levels). Synced from gateway `QuorumConfigSchema`.
- `src/config/schema.js`: `base_confidence` field added to `MemberSchema` (required for `POST /config/upload` alignment with gateway validation).
- `src/config/schema.js`: `is_hierarchy_anchor: z.boolean().default(false)` added to `QuorumConfigSchema` (2026-07-06) — marks org/group/division/department scaffolding configs so `syncOneProject()` (gateway `routes/sync.js`) skips their DynamoDB membership sync; without it, every anchor node's `members` entry (required for owner/PA validation) leaked into real users' project lists. Synced to gateway `gateway/src/shared/config/schema.js` in the same commit.
- `src/tools/search.js` / `src/tools/recall.js`: fixed `resolveGlobals()` being called with `ctx.projectId` (internal Postgres id, e.g. `q_p13`) instead of `ctx.groupId` (human-facing slug, e.g. `busy-hopper`) — the gateway's `GET /config/:projectId` route checks the path param against `req.user.project`, which is always the group_id, so passing the internal id 403'd and silently degraded every search/recall to project-scoped-only (no global catalog federation). Fixed by passing `ctx?.groupId ?? projectId` in both files.
- `src/tools/search.js`: added `settleWithConcurrency()` + `SEARCH_CONCURRENCY = 4` — caps how many Graphiti calls `search()` fires at once (previously all `1 + 1 + globals.length` calls fired simultaneously via `Promise.allSettled`). Root cause: `graphiti-core`'s `FalkorDriver.clone(database)` re-instantiates the driver per `group_id`, and every instantiation unconditionally re-runs `build_indices_and_constraints()` (~15-20 index queries, no "already built" cache) — with many linked global catalogs, firing all per-catalog searches at once floods FalkorDB with enough concurrent queries to exhaust the client-side redis-py connection pool (`MaxConnectionsError`), stalling every call until the MCP client's own 30s `AbortSignal` fires. Throttling client-side concurrency is a mitigation, not the upstream fix — the real fix (caching per-driver "indices built" state) belongs in the `quorum-graphiti` fork per the workspace root `CLAUDE.md`'s Graphiti fork rules. **Underlying pool exhaustion (2026-07-14):** `redis-py`'s async `ConnectionPool` hardcodes `max_connections=100` when the FalkorDB client doesn't pass one — confirmed via `FalkorDB` → `redis/asyncio/connection.py`. A prior storm left exactly 100 connections permanently stuck `in_use` inside the already-running `quorum-graphiti-1` container (~10h old, never released) — a client-side throttle alone cannot free connections already wedged in another process's memory. Fixed live by `docker restart quorum-graphiti-1` (resets the in-memory pool); the throttle above prevents a *fresh* storm from recreating the leak. No source change needed for this half.
- `src/graph/client.js` `callGraphiti()` (2026-07-14): the stale-session reset only checked `response.status === 400` — Graphiti's actual "Session not found" error (e.g. after the Graphiti container restarts and drops its session store, as above) comes back as **404**, so `_sessionId` was never cleared and every subsequent call kept resending a dead session forever. Fixed by widening both the reset guard (`!response.ok` branch) and the retry-continue guard (`catch` block) to also match `404`. Note: this file's raw MCP session-handshake code (`initSession`, `_sessionId`) is exercised when quorum-mcp talks to Graphiti directly; the JWT/gateway-proxy path noted above (`getProjectId()` fix) is a separate mode and was already confirmed to have no counterpart in the gateway's copy. The identical bug (and identical fix) was independently present in `gateway/src/shared/graph/client.js`'s own direct-to-Graphiti `callGraphiti()` — fixed there in the same pass since it's the copy actually exercised when MCP tool calls are proxied through the gateway.
